Stop Treating Agent Memory Like Chat History

Most enterprise agents still confuse two very different things: the transcript of this conversation, and the facts that should survive the next one.

Session history is short-term context. It is the chronological list of messages and tool calls for a single interaction. When the window ends, that transcript is no longer the right place to store “user prefers Python,” “works on the EMEA finance team,” or “already completed the security review for project Atlas.”

Long-term memory is different. It is a curated set of facts, scoped to an identity, that the agent can retrieve days later. On Gemini Enterprise Agent Platform, that plane is Memory Bank. Getting it right is less about enabling a toggle and more about designing when conversation becomes durable knowledge.

Two generation patterns

There are two first-class ways to turn conversation into memory.

GenerateMemories is the immediate path. You point it at an Agent Platform session (or pass events directly in the payload), set a scope, and kick off extraction and consolidation as a long-running operation. Use it when you have a clear lifecycle moment: end of session, end of a task, or a scheduled checkpoint. In production, run it in the background. Waiting on completion adds latency the end user does not need.

IngestEvents is the streaming path. You continuously append events into a buffer defined by scope plus stream_id. Memory Bank decides when to flush based on rules you configure: event count, idle duration, fixed interval, or an explicit force flush. Overlapping event windows keep consecutive flushes coherent. If nothing triggers, pending events still flush after 24 hours so abandoned streams are not lost forever.

Architecturally, pick GenerateMemories when your agent owns discrete conversation boundaries. Pick IngestEvents when events arrive as a continuous stream from multiple writers or when you do not want every client to decide “now generate.”

Topics decide what is worth remembering

Memory Bank does not persist everything. It extracts against memory topics.

Managed topics cover the common cases: personal information, preferences, key conversation outcomes, and explicit remember or forget instructions. Custom topics let you define domain-specific extraction with a label, a description, and preferably few-shot examples so the extractor knows what “meaningful” means in your business.

If you skip topic design, you get either noisy memories that pollute the prompt or empty memory banks that never personalize. Treat topics like a schema for personalization, reviewed the same way you would review a data contract.

Consolidation is the hard part

Extraction alone is not enough. New facts must merge with what already exists for the same scope. Memory Bank consolidates: create when the concept is new, update when it overlaps, delete when new information contradicts the old fact.

That consolidation behavior is why scope design matters. Memories consolidate only within a scope. Scope by user alone if every agent should share one personalization profile. Add agent or session dimensions when you need isolation. Attach metadata and choose a merge strategy when you need finer control over which memories are eligible to update each other.

Poisoning and residency are governance, not footnotes

Long-term memory raises the blast radius of a bad turn. If an attacker or a confused user plants a false fact, the agent may keep acting on it across sessions. That is memory poisoning. Mitigate it the same way you mitigate other generative risk: screen inputs on the write path (for example with Model Armor), red-team the memory loop, and keep high-impact side effects sandboxed or human-reviewed.
