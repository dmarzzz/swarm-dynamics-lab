# Using this toolkit in swarm-dynamics-lab

This is **general methods and development tooling**, owned initially by `vishesh/codex-methods` under task `build-agent-experiment-toolkit`. It supports whichever research question the team later approves. It neither chooses that question nor advances its research status.

## Where each kind of work belongs

| Material | Location | Required status |
| --- | --- | --- |
| Shared methods, reusable manifests/schemas and offline teaching code | `5-experiments/toolkit/agent-experiments/` | Build task; local checks |
| Canonical paper metadata and source-specific limitations | `1-library/papers/` | Opened primary source; truthful reading depth |
| Question-specific prior-art synthesis | `2-surveys/` | Gate must pass before hypotheses; cross-researcher review for promotion |
| Testable team claim | `4-hypotheses/` | Existing survey requirements and independent review |
| Actual project protocol, implementation and measured results | `5-experiments/<id>/` | Accepted hypothesis; protocol and metrics committed before real collection |
| Generated raw toy traces and local inputs | `data/<run-id>/` | Git-ignored; no secrets in exports |
| Final outward-facing deliverable | Flight Deck `artifacts/` | File only through `.flightdeck/fd.py add` with safe provenance |

The annotated bibliography here is a **methods reading guide**, not a formal `2-surveys/` submission. Its 29 references do not imply that the full-read, citation-chasing, source-type or saturation requirements passed. The synthetic worked example teaches controls and accounting; it is not a proposed team hypothesis hidden outside the gate. No new formal survey, hypothesis, experiment or review status is introduced by this contribution.

## Required setup workflow

For every new experimental question or material revision, follow [EXPERIMENT-SETUP.md](EXPERIMENT-SETUP.md), create an owned study `SETUP.md` from [the template](templates/experiment-setup.md), and keep gate evidence and handoff status current. This is required by the shared AGENTS.md. Existing formal research gates and researcher-specific resource authority remain in force.

## Start here before a project is selected

Read [GUIDE.md](GUIDE.md) for units, estimands, budgets and statistical design. Use [HARNESS.md](HARNESS.md) to choose an implementation architecture. Copy the [protocol template](templates/protocol.md) while drafting, but do not mistake unfilled fields or a hash for preregistration. The guide's templates supplement the lab's existing templates; they do not replace them or weaken validation.

From the repository root, validate without network or credentials:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 5-experiments/toolkit/agent-experiments/scripts/validate.py
python3 5-experiments/toolkit/agent-experiments/scripts/toy_harness.py \
  --config 5-experiments/toolkit/agent-experiments/examples/collective-sensing/config.json \
  --out data/agent-experiment-teaching-run
```

Use a new output directory on each invocation. The output is generated by deterministic scripted majority rules. There is no provider adapter and no paid execution path. The run template's zero-dollar cap is an example setting, not a security boundary for future software; a real adapter must enforce its own budget and permissions.

## Promote methods into an approved project

1. Follow `AGENTS.md`: register an agent, claim the appropriate task and keep status/logs current.
2. Build the question-specific source catalog and survey using canonical `[[library-id]]` citations. Existing records remain authoritative; append notes rather than overwriting another adder's work.
3. Pass the survey gate and required cross-researcher review; obtain acceptance of the specific hypothesis. This methods package does not satisfy those gates on its own.
4. Create the real experiment with `python3 scripts/lab.py new experiment <id> --agent <researcher>/<agent>`. Retain its required Setup, Protocol, Metrics, Results and Analysis sections. Link a filled copy of this toolkit's extended protocol from `## Protocol`.
5. Put implementation under `5-experiments/<id>/src/` and small outputs under its `results/`, following the repository's size rules. Resolve all model/configuration placeholders. Keep large traces and restricted inputs in `data/` or an approved external store.
6. Record the toolkit commit, exact configuration and source hashes used. Freeze project-specific code, scorer, data and schedule; run a separate engineering pilot. The toy's variance assumptions are not pilot estimates for the new task.
7. Commit protocol and metrics before the first real run. Record dated amendments, all failed attempts, cost and human intervention. Validate isolation and adapters before any paid or external action.
8. Update the hypothesis only from the resulting evidence, then file outward-facing artifacts through Flight Deck. Use a public-safe provenance description; never copy a prompt containing credentials or private context into artifact metadata.

## How this stays useful across project choices

These are adaptation patterns, not claims of novelty or recommendations to bypass review.

| Research family | Reusable part | What the project must supply |
| --- | --- | --- |
| Collective sensing / quorum | Paired observations, source identity, whole-world units | Ground truth and realistic observation/error model |
| External influence / retrieval manipulation | Access manifests, treatment diffs, held-out scenarios | Legitimate utility rubric; attacker remains outside the target swarm when that is the threat model |
| Fork/merge integrity | Immutable definitions, event lineage, protected evaluator | Merge semantics, corruption model and accepted intervention |
| Sybil resistance | Independent-source accounting, population-size treatment | Identity model and explicit independence assumptions |
| Swarm detection | Scenario sampling, calibrated judges, uncertainty | Labeled traces, base-rate assumptions and out-of-sample validation |
| Agent-assisted discovery | Claim-to-evidence ledger, protected verification | Domain-specific novelty assessment and independent scientific validation |

## Maintenance and contribution boundaries

The package is deliberately self-contained. Repository checks still run through `scripts/lab.py check`; the additional workflow tests only this tooling and has read-only repository permissions. It performs no model calls or external publication. Existing generated dashboards and Flight Deck manifests are untouched.

Tests require Python 3.10+ and only its standard library; repository validation additionally uses the repository's declared PyYAML dependency. The schema checker implements only the documented subset. Production harnesses should use full schema validation, appropriate sandboxing, durable logging and tested failure handling.

Before editing the toolkit, claim a new build task and record ownership in that task. Keep paper-reading claims conservative. Do not duplicate canonical library records because a journal title differs from a preprint title. Update the literature status with an evidence link when a paper is published or corrected. Licensing of third-party papers/software remains with their respective sources; this contribution does not invent a license for the repository.
