# Immune Response — proposed contract discriminator

Prospective preparation after A10. **Not launched; requires an owner decision on this changed execution contract.** A10 remains frozen and its failed scores are unchanged.

A10 established useful runtime repair by both stronger models, but not reliable restraint or configuration repair. Every action response serialized `action_id` before `reason`. Several explanations later corrected the already-selected action. This makes output ordering a plausible architectural contributor, not a proven cause. A separate defect is that `failed_service` and `fault` did not define their exact scoring conventions clearly enough.

The prepared candidate defines `failed_service` as a *currently observed non-live process*, not the service implicated in a configuration mismatch. It defines the fault priority explicitly: visible configuration violation; otherwise unknown if liveness is stale; otherwise runtime failure; otherwise none. These definitions express the existing scorer, rather than changing truth or relaxing outcomes.

A proposed A11 would use Opus4.6, the same four development roots, the same diagnosis definitions, tool effects, two-tick horizon and two calls per tick in both arms. Compare action-first versus a brief evidence-based justification first, followed by the selected action. No hidden reasoning is requested, no simulator truth is injected, and no deterministic action filter rescues choices. Keep the same 512-token output and 8000-byte request bounds. Alternate arm order across roots. Inspect actual response key ordering; a failure to deliver the assigned order is a manipulation failure, not a behavioral result.

The development comparison is 4 roots × 2 arms × 2 ticks × 2 calls = 32 calls. These are paired authored roots, not 32 independent units. All fixed diagnosis and service-outcome gates plus manual action/explanation consistency must pass for the justification-first candidate before opening the still-unconsumed four-case Opus holdout packet (16 more calls). Do not reuse Sonnet cases as newly unseen data. Stop on provider/schema/usage failure, failed candidate qualification or failed holdout; no further model escalation. Correct/stale/incorrect advice remains a later unopened test, not supported by this comparison.
