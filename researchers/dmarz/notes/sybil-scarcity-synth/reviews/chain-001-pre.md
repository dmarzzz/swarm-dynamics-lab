- Question and decision: when a rare fact's truthful reports are outnumbered by repeated fabricated reports, does a stated evidence rule, or higher reasoning effort, reduce how often the synthesizer answers with the fabricated value, and what does it cost in accuracy at 27 and 81 carriers? It tells us whether the earlier collapse can be addressed at the synthesizer or needs to be addressed at admission.
- Expected finding: the rule lowers the fabricated-answer rate at 1 carrier (predicted direction, marker 10 points), mostly by abstaining, and costs accuracy at 27 carriers. Plausible negative results: at effort low the model ignores the rule (contrast near zero); or it over-applies it and abstains on clean packets, which stops the chain at Q0. The run is uninformative if Q0 fails for the base prompt, if the base/low cells do not reproduce the earlier collapse on the fresh roots, or if invariance checks report violations.

- Gates and what happens when one fails:
  - Before every stage `coordinator.enqueue` requires exactly one run of the previous stage for the same model at this source hash, `done`, `invalid == 0`, `qualification_passed == 1` (S0 is model-free; a continuation chain after a billing stop counts as one run), and refuses a batch name that exists. A refusal stops the chain with exit code 3; nothing is queued.
  - S0 fails if any of 128 rows is invalid, the scripted qualification fails or any of 27 invariants is false. Nothing paid has happened.
  - P0 fails unless the one response parses, the model id matches, usage is reported, the stop reason is `end_turn` and the six values equal the expected values.
  - Q0 fails unless every configuration has 12 valid packets, at least 69 of 72 fields, at least 11 exact packets and null on all 6 withheld rare fields. Q0 is strict: the first failed call stops it. S1 is never queued.
  - Before S1: 480 × Q0's mean cost per low-effort call + 480 × Q0's mean cost per high-effort call must be at most the remaining cap; otherwise `projection_exceeds_cap`.
  - S1: see the failure rule below.
- Failure-handling rule of 2026-10-04, required by dmarz/fleet-monitor; the package adopts all four parts:
  1. Evidence: a failed HTTP request keeps `http_status`, `error_body` (2,000 characters) and `request_id`; never a request header, the key or the workspace id.
  2. The token count never fails a call: retry rule for 429 and 529, one re-send after 2 s for anything else, then the byte-length fallback (`count_fallback`).
  3. S1 tolerates failed calls up to `max_failed` = **10** (the larger of 3 and 1% of 960); integrity failures stop at once; S0, P0 and Q0 stay strict.
  4. Billing outage: re-send the same call every **60 s for up to 1,200 s**; then stop with `provider_credit_balance_low`, units not started, reservation released; `python src/chain.py resume` continues with batch `s1-001-r1`.
- Model ladder: `[claude-opus-5-5, claude-opus-5]`; the model of an attempt comes from `STUDY_MODEL`. The second model is used only after a limit or credit refusal that did not clear in 20 minutes, with its own batches, P0, Q0, ledger and directory, as a dated amendment noted on the run request. Never pooled. Documentation checked is listed in the README.
- Hard maximums (all in the hashed design, per model attempt): calls P0 1, Q0 48, S1 960, total 1,009; transport attempts 1,300; 2 requests in flight; 600 s per request including retries; 28,800 s per stage; 32,400 s for the chain, of which the last 600 s are kept for draining and uploads; USD 240 of settled cost plus open reservations.
