# Pre-registration: verify-cost-qwen, attempt 001

Frozen 2026-10-04 by dmarz/pipeline-verify, before any code of this study existed and before any run. No stage has run and no model call has been made. Exploratory; S2 disabled; no novelty claim. Machine-readable values are in [design.yaml](design.yaml).

Source of the design: research program v5, line V ("When is verification worth its cost?", sections "Follow-up V", session brief 3 and the Verification paragraph of "Qualification for the three focused follow-ups"). The design is the program's and is implemented as written. Where the program leaves a choice open, this file states the choice and why (item 17).

1. **Primary descriptive contrast.** For each main layout, the mean over the twelve cases of expected regret with the `table` representation minus expected regret with the `prose` representation. 24 paired layout-level values. Predicted direction: negative. Practical marker: 0.03 expected-loss units per decision. The design bounds the contrast at ±0.3208. A small, uncertain or positive contrast is a valid outcome.
2. **Units.** 24 layouts, seeds 3000 to 3023. A layout fixes the reported cell, the cell without evidence, the report's label, the 34 direct measurements and the order of the two legal cells. The 24 requests of a layout share all of that and are dependent. The twelve cases are authored, not sampled. The independent randomized units are 24 layouts within twelve authored cases, not 576 independent tasks. No power claim.
3. **Decision and scoring.** One inspection; legal cells are the reported cell and the cell without evidence, always both. Check (inspect the reported cell): the other cell is returned UNKNOWN, loss U. Explore (inspect the cell without evidence): the report is kept, loss 1 with probability e. Expected loss: U for check, e for explore. Minimum-loss action: check if e > U, explore if e < U. Expected regret = expected loss − min(e, U). The realized loss under the layout's seeded truth draw is secondary and never defines the optimum. This is the PC5 rule with the UNKNOWN cost 0.25 replaced by U and reliability replaced by 1 − e.
4. **Cases.** e in {0.05, 0.20, 0.50, 0.80} × U in {0.10, 0.25, 0.75}. Optimal action: check for (0.20, 0.10), (0.50, 0.10), (0.50, 0.25), (0.80, 0.10), (0.80, 0.25), (0.80, 0.75); explore for the other six. Regret of the wrong action is |e − U|: between 0.05 and 0.70.
5. **Representations.** Both requests hold the same system prompt, map, evidence, objective, legal cells and answer instruction, byte for byte, and the same six consequence records (action, cell, outcome, probability, cost). `prose` renders the records as sentences, `table` as rows. Neither states an expected loss, compares the actions or recommends one. Offline tests prove: each block parses back to the records; the records of the two blocks are equal; re-rendering the parsed records reproduces each block exactly; the numbers, cells and labels in the two blocks are the same multisets.
6. **Manipulation fidelity.** Within a layout, the request text with the three numbers e, 1 − e and U masked is identical across the twelve cases of a representation. The listing order (report first on even seeds) and the report label are balanced over the 24 layouts: 6 layouts per combination.
7. **Offline comparators.** Always-check (mean regret 0.1500), always-explore (0.1708), always-first and always-second listed cell, and the analytic policy (0). Computed offline per case and per layout. They are not model arms.
8. **Stages and gates.** S0 scripted (144 rows, 0 calls), P0 one call, Q0 23 calls, S1 576 calls. Batches `s0-001`, `p0-001`, `q0-001`, `s1-001`. A stage is queued only when exactly one run of the previous stage exists at the same source hash and it is `done` with `invalid == 0` and `qualification_passed == 1`. A batch name is never reused.
9. **S0 acceptance.** All 144 rows valid; the analytic policy passes the qualification gate on set a and on set b; every invariant of README "Protocol" item 1 holds, including: the optimum changes across the twelve cases (six and six), the four constant policies fail qualification, and each qualification fixture has both actions legal and an expected-loss margin of at least 0.60.
10. **P0 acceptance.** One call on the first fixture of the active qualification set. Passes only if the response parses as JSON, the model slug is `qwen/qwen3.7-flash` or its dated form, the response names its provider and it is Alibaba, usage is reported, the finish reason is `stop`, no reasoning tokens are reported and the answer is structurally valid. Whether the choice is optimal is counted in the qualification gate, not in P0's gate.
11. **Q0 acceptance (the program's thresholds, unchanged).** Twelve disjoint clear-dominance choices × two representations = 24 fixtures, both actions legal: P0's row plus Q0's 23 rows. Required: 24 of 24 structurally valid and at least 11 of 12 optimal in each representation. The fixtures are in `design.yaml` (`qualification.fixtures_a`); none is a main-grid case; six make checking optimal and six exploring; within each six the listing order is balanced. A failed qualification stops the chain before S1.
12. **The one repair.** After a failed qualification the failing answers are read first (rendered request and returned text for every miss). At most one bounded repair may follow, as attempt 002: `qualification.set: b` (the second, disjoint set of 24 fixtures frozen in `design.yaml` today, layouts 2900 to 2911), a new source hash and its own pre-run review. This is the only repair. A failed repeat ends the line. Thresholds are never lowered.
13. **Actor.** `qwen/qwen3.7-flash` via OpenRouter; request body exactly the frozen template (`model`, `provider {only: [alibaba], allow_fallbacks: false, require_parameters: true}`, `reasoning {enabled: false}`, `max_tokens: 1000`, `response_format {type: json_object}`) plus `messages` (one system and one user message). Local validation: the answer must be a JSON object with exactly the key `inspect` whose value is one of the two legal cell names as a string. An invalid JSON or invalid answer is a failed call. No repair call, no answer retry, no memory across calls.
14. **Execution limits and failure handling.** Four requests in flight; 120 s per request; 5,400 s per stage; 7,200 s for the chain. Ledger caps: P0 1, Q0 23, S1 576, 600 for this attempt (the ledger's study cap is 624: this attempt plus the 24 qualification calls of the one permitted repair); 784 transport attempts; USD 2 of settled cost plus open reservations. Reservation: 10 times (request bytes as the input-token bound plus 1,000 output tokens, at USD 0.03 and USD 0.13 per million tokens). Transport retry: at most 2 re-sends per call, only for HTTP 429, 502, 503 and 529, backoff 2 s then 6 s, `retry-after` honoured up to 20 s, inside the one request timeout; timeouts, other statuses and every answer are never retried. Failure-handling rule of 2026-10-04: (1) every failed request keeps its HTTP status, response body (first 2,000 characters) and request id, never a request header or the key; (2) does not apply, because this route has no token-counting endpoint and the reservation is the byte bound; (3) in S1 a call without a valid answer is recorded as failed and dispatch continues until more than `max_failed` = 6 calls have failed (the larger of 3 and 1% of 576); integrity failures (a ledger refusal, a breached reservation, a model or provider mismatch, a source or batch mismatch, a deadline) stop dispatch at once; S0, P0 and Q0 stay strict; (4) a billing or limit refusal (HTTP 402, or 400, 403 or 429 whose body names credit, balance, billing, a usage or spend limit, an exceeded limit or insufficient funds) pauses the whole stage, the same call is re-sent every 60 s for up to 1,200 s, nothing is recorded as a model outcome meanwhile, and if the outage outlasts the limit the stage stops with `provider_credit_balance_low` and the unfinished units are recorded as not started. Before S1 the chain stops with `projection_exceeds_cap` if 576 × Q0's measured mean cost per call exceeds the remaining cap, and with `input_ceiling_projection` if P0's measured input tokens per byte times the largest S1 request exceeds 8,000 tokens.
15. **Resume after a billing stop (dated 2026-10-04, pre-registered).** Units left not started by a `provider_credit_balance_low` stop may be resumed at the same source hash, as a dated amendment recorded in this folder, because a billing outage is unrelated to outcomes. `python src/chain.py resume` queues a continuation batch `s1-001-r1` (then `-r2`, ...) holding exactly the not-started units, under the same ledger. A call that a billing stop left unanswered has its reservation voided in the ledger (no model ran), so the continuation runs inside the exact S1 cap: standing S1 reservations, answered or open, never exceed 576, and no unit is answered twice. The analysis reads the original run and its continuations together and counts every unit once.
16. **Analysis.** All 24 layouts are retained. Complete-case estimate: over layouts whose 24 units are all valid, the mean of the 24 layout values, its standard error, a descriptive 95% t interval, the range and the leave-one-layout-out range, with the number of layouts as denominator. Missing-data rule: a failed or not-started unit stays in its cell's denominator with its regret bounded between 0 and |e − U|; the primary contrast is then also reported as bounds over all 24 assigned layouts. Nothing is dropped, imputed or re-run. Reported for every one of the twelve strata and both representations: assigned, valid, optimal, check and explore counts, mean regret, paired difference. Reliable-source regression: in each stratum with e ≤ 0.20, the optimal count with the table minus the optimal count with the prose; a drop of 3 or more of 24 is flagged and reported next to the primary, whatever the sign of the primary. Secondary and descriptive: position (first-listed share), realized scripted loss, comparison with the offline comparators. No multiple-testing claim and no confirmatory claim.
17. **Choices this file makes where the program is silent, with reasons.** (a) "Full action consequences" are the outcome, probability and cost of each affected cell under each action; the expected loss of an action is not printed in either representation, because printing it would reduce the task to comparing two printed numbers. (b) The answer holds only the chosen cell; no rationale field, because the program specifies reasoning disabled and a one-step choice. (c) "Clear dominance" in qualification means an expected-loss margin |e − U| of at least 0.60 with both actions legal. (d) The order of the two legal cells and the report label are balanced over layouts by construction instead of drawn (PC5 drew the order). (e) Reliable-source strata are those with e ≤ 0.20, which contains PC5's reliable condition (reliability 0.8).
18. **Stop rules.** No answer retries, no replacement runs, no change of sample, thresholds or cases after outcomes are seen. Null and adverse results complete the study. S2 and task ids 10000 to 19999 stay closed.
19. **Review status and authority (2026-10-04, as relayed to this builder by dmarz/pipeline).** dmarz directed this program himself (research program v5, written with him by a Codex session on 2026-10-04; his instruction to ship it was relayed by dmarz/fleet-monitor). The design is the program's; this package implements line V as specified there. Cross-researcher review is waived by dmarz for these exploratory runs; dmarz/fleet-monitor's check is a same-researcher check and nothing more; the run is not independently reviewed. Implementation note of the same date: the program's five-session and shared-reservation arrangement is replaced by the ready-chain (one package per line, one server per line, its own ledger and caps, launched by the orchestrator from the private run queue). Cost is not the gate; the call caps are hard, and actual calls, tokens and dollars are reported to the hub.

## Changes after the first version of this file, all on 2026-10-04 and before any run

The first version was committed before any code existed (commit `65b4497f`). These changes were made while the package was built. No stage had run and no model call had been made.

- Item 15 first said that a continuation after a billing stop raises the S1 cap and the study cap by the number of unanswered reservations. The pipeline's revised reference adapter (main `639e9501`, required by dmarz/pipeline for all three follow-up lines) voids the reservation of a call that a billing stop left unanswered, so the continuation runs inside the exact S1 cap. Item 15 now states the void rule.
- Item 14: the reservation carries a 10 times margin over the snapshot-price bound (required by dmarz/fleet-monitor's standby pre-review, so that a provider-reported cost above the snapshot prices does not stop a stage over fractions of a cent); the ledger's study cap is 624 instead of 600 (call caps are counted per batch family, so the one permitted repair attempt has its own 24-call qualification allowance in the same ledger; this attempt's caps are unchanged at 1, 23 and 576); 784 transport attempts instead of 760; the billing detector also covers HTTP 429 and bodies naming billing, a usage or spend limit, an exceeded limit or insufficient funds.
- Item 10: a response that does not name its provider fails the probe (the first adapter accepted it).
- Item 13 is unchanged; the adapter additionally rejects an answer whose JSON object repeats a key.

The comparison, the cases, the representations, the layouts, the qualification fixtures and thresholds, and the analysis (items 1 to 9, 11, 12, 16 to 18) have not changed.
