# Scenario and parameter ledger

RD-1. Conditions are a design space, not a claim that a full Cartesian sweep is implemented or affordable. Core factors below are implemented first; extensions require a versioned plan. Truth and condition labels belong only to the evaluator.

| Factor | Core values / construction | Why it matters | Control |
|---|---|---|---|
| Majority correctness | correct, wrong; both PROCEED/HOLD | Correction versus corruption | Paired balanced labels |
| Minority correctness | correct, wrong, irrelevant, absent | Avoid guaranteed truth-teller | Never expose label to actors |
| Team size and minority fraction | Five scripted votes initially; later 3/5/9 agents and 1 or 2 dissenters | Numerical pressure | Unique evidence fixed in duplicate contrast |
| Source ancestry | One shared root versus distinct roots; copied reports | Votes need not be observations | Full versus partial lineage separate |
| Evidence quality | Exact fixture reference; noisy/incorrect check condition | A verifier can also be wrong | Distinct primary observation channel |
| Scope | Matching/wrong object, build, platform or capability | Impressive evidence may be irrelevant | Neutral metadata and equal-length records |
| Freshness | Current, expired, superseded | New evidence versus old truth | Logical timestamps; known TTL |
| Challenge content | Supported, unsupported, missing citation, same repeated claim | Dissent quality | Syntax checks common across arms |
| Withholding | Initial explicit challenge versus no challenge | Admission is separate from expression | Natural-minority stage later |
| Tool access | Available, unavailable, timeout; one static check | Practical verification limits | Same allowed tool across arms |
| Deadline and check delay | Two-tick default deadline; one-tick check; late variant | Accurate but late can fail | Logical and wall clocks separate |
| Repetition | Same evidence ID/root; new evidence after closure | Prevent unlimited interruption | Claim fingerprint with scope and version |
| World changes | Static; safe→unsafe; unsafe→safe | Reopen without permanent stigma | Previous alarm identity counterbalanced |
| Loss asymmetry | Wrong proceed/hold/defer/check costs | Risk-sensitive utility | Report raw counts and a sensitivity surface |
| Role and identity | Neutral IDs, shuffled order; no truth-role names | Authority leakage | Identity-swapped metamorphic check |
| Model behavior | Pinned Jev, returned distributions, schema failures | Typed output is not correctness | Native wire validation; no retries hidden |
| Memory | Recorded closure ledger, TTL and claim scope | Hysteresis versus stale state | Reset and retained-state extension |
| Network topology | Shared review channel initially | Local inhibition may differ | Ring/modular graphs are future extension |
| Credibility history | No learned reputation initially | A past error must not erase future evidence | Reliability learning is future extension |
| Multiple challengers | One challenge opportunity per step initially | Queueing can become a separate study | Bursty adversaries deferred |
| Language and representation | Fixed English templates initially | Text complexity and parsing artifacts | Paraphrases/other languages later, held out |
| Natural formation | Scripted causal screen; separate private-vote qualification | Avoid selecting only interesting majorities | All roots kept in main denominator |

Initial scenario cells: clean disagreement, misleading disagreement, wrong-scope challenge, stale challenge, unavailable check, late check, repeated closure and genuine new evidence. Software tests may enumerate development fixtures. Neither reserved native qualification seeds nor confirmatory seeds are used for development demonstrations.

Power and cost require measured qualification accuracy, variance and latency. No sample size is advertised as sufficient before those exist. Fix a minimum useful policy effect and an acceptable harmful-reversal ceiling with the reviewer before confirmatory assignment generation.
