# PI assessment of A3 and decision for A4

A3 is credible as a narrow negative diagnostic, not as evidence of robust autonomous recovery. Its execution, paired proposal reuse, measured usage and preserved failures are strengths. The remedy is to create a meaningful information problem, not enlarge a ceiling task or strengthen a prompt until it passes.

1. **Construct validity:** static contracts and process health were conflated. A same-version deployment was counted without distinguishing a useful restart from redundant mutation. A4 models process liveness separately and never imputes downtime merely because a deployment occurred.
2. **Scenario independence:** stale_advice and registry_partition shared the same initial state and solution; registry failure mattered only if the agent chose a dispensable tool. A4 retains the unavailable-registry case as a resilience control, not a second independent repair mechanism; introduces a concealed runtime crash and stale false alarm with different optimal decisions.
3. **Treatment strength:** A3 checked a field the controller could copy directly; it did not control correctness of reasoning. A4 checks observable provenance/epoch only, and tests whether that annotation changes information acquisition. It still cannot certify action correctness.
4. **Baselines:** a deterministic visible-information controller establishes feasibility and a stale-trusting controller establishes sensitivity. Neither is a model-performance result. Both receipt arms get identical evidence and shared reviewer text; no oracle gate mechanically forces the desired outcome.
5. **Power and realism:** six fixed cases support failure discovery, not effect prevalence. Avoid decorative agent counts and broad immune-system rhetoric. Future realistic incident traces would be a separately scoped study, not a claim attached to this simulator.
6. **Measurement:** retain customer availability, unnecessary intervention and invalid execution as separate outcomes. Preserve A3's failed gate rather than changing its score retrospectively.
7. **Visualization:** health-only plots hid the central failure. Plot every mutation, useful versus redundant restarts, evidence freshness and inspections alongside health.
8. **Iteration discipline:** preserve original cap and ledger; maximum two60-call attempts in this cycle, with a post-mortem between them. Stop for a valid null without further decision value; do not hunt for significance.

Owner's current request authorizes implementing this PI-led revision and running the bounded runbook cycle. Additional researcher review remains waived. Infrastructure/account verification, immutable plans and preflight evidence remain mandatory. This is the operator's assessment, not an independent PI review.
