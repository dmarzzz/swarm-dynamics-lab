# Immune Response — C1 action-order discriminator

## TLDR

Prospective packet, not funded or launched. On four previously inspected development worlds, compare Opus 4.6 action-first versus brief observable justification-first serialization. Both arms use identical explicit diagnosis definitions, observations, actions and budgets. Eight trajectories, two ticks and two calls per tick: exactly 32 maximum calls. Measure executed outcomes, diagnosis accuracy, actual field ordering and action/explanation agreement. Fixed outcome thresholds; no rescues or model escalation. Authored small paired discriminator, not fresh-run reproducibility or an immune-swarm efficacy result.

## Question and prediction

A10 recorded three cases where later prose contradicted the selected action, with action_id emitted first in every response. Does moving the brief observable justification before action_id reduce these contradictions and improve effective choices? This tests a serialization/instruction-order package, not access to hidden reasoning. Both arms share clearer diagnosis definitions; A10 historical counts are not a causal comparator for this change.

## Setup

Four A10 development roots: healthy service, worker crash, stale false alarm and configuration incompatibility. No holdouts or twelve-world panel are consumed by C1. Alternating arm order by root is fixed in packet.json; cases are reset and each model call has a new explicit context. Runtime observation includes only public catalog, deployed versions, probe history and legal actions. The action stage receives the diagnosis unchanged. No private operator memory, source labels or simulator truth reaches the model.

Opus4.6 via Anthropic-only OpenRouter, no fallback; temperature0, reasoning disabled, max512 output tokens, max8000 wire bytes. Both arms use exactly the same action schema fields; only property/required ordering and the instruction specifying that order differ. No gold correction, deterministic action veto or retry.

A separate public-observation rule comparator computes catalog constraints, inspects stale liveness, restarts a currently failed process and enumerates a single compatible deployment. It is a strong feasible comparator for these authored one-fault/two-tick cases, not a general planner: no multi-fault recovery, unknown catalogs, sensor deception or unmodeled deployment dynamics. It receives no case identifiers, gold actions or hidden state. Absence of advice is an LLM control condition, not this rule comparator. Any future advice is authored controlled content, not a natural peer swarm.

## Protocol

One rollout per root/arm; four paired root units, not eight independent tasks or32 independent calls. All eight assigned trajectories run through valid wrong actions, retaining failures. Stop transport/schema/usage/route failures and duplicate or incorrect field ordering; record ordering failure as manipulation/protocol failure, not task incompetence. No automatic successor, holdout stage, repair sweep or additional model.

The hosted JSON field order is verified from the actual returned content before executing an action. Offline tests cover both successful and ignored ordering. Raw returned content and request hashes remain available to audit ordering and semantic agreement. Manual review evaluates every action/explanation pair after collection; an auto-generated pass cannot grant successor readiness.
