# Immune Response — verification-required loop (prospective, offline only)

## TLDR

Compare the existing public-evidence deployment guard with the same guard plus a required inspection after mutation. Test successful, failed-first and delayed repairs, genuine RPC/data compatibility faults, and already healthy service. The four-tick tool budget and two model-call slots per tick are identical. An architecture-supplied inspection is never scored as model initiative. This is an unfunded prospective successor to verification v1; no native dispatch or allocation is authorized.

## Question and prediction

Can a verification-required loop complete real repair verification while retaining protection against unnecessary intervention, including when the first repair fails or remains pending? V1 found correct diagnosis in all96calls but unnecessary post-repair proposals in8/24fault episodes; the guard blocked execution without producing inspection. The successor tests whether an explicit verification obligation closes that gap without preventing a genuinely necessary second repair or a configuration change.

Required inspection will mechanically provide evidence when it executes. That is a declared architectural mechanism, not an empirical discovery or learned competence. The empirical unknown is whether the controller uses the resulting evidence to finish the required work, select a genuine configuration repair, and avoid unnecessary follow-up proposals. Missed repairs, delay and false intervention remain visible; a result need not favor the new loop.

## Setup

Use Opus4.6 with separate factual diagnosis and uncorrected justification-first action selection. Both arms use the same public-evidence guard, prompts, action schema, initial observations and four scheduled decision ticks. The verification-required arm substitutes `inspect` on a tick with an outstanding post-mutation verification obligation; this consumes that tick and its service opportunity rules. Both still produce diagnosis and action proposals at every tick, so proposal quality and proposed inspection can be measured under equal model-call budgets. The guard-only arm executes an admitted proposal or a refused-action wait. An explicit substitution/denial and the actual observation are retained in history. No oracle repair is substituted.

Construct two runtime incident roots, each with three paired hidden response mechanisms: an immediate successful restart, a first acknowledged restart with no effect followed by a successful retry, and an acknowledged restart completing before the third decision tick. Within each root the initial public observation is identical across mechanisms. Acknowledgement is not success; failed versus successful completion is learned through inspection. Pending/completed operation status is public and never implies health. Background completion advances the world epoch and invalidates an earlier probe.

Add two distinct configuration roots: a live worker with an incompatible RPC interface, and a live worker unable to read the persisted data format. A compatible single-component deployment is necessary; “restart current binary” cannot fix either. Add two healthy controls. This is six task roots and ten branch worlds, not ten independent mechanisms. Service aliases and versions vary within shared generators; these variations do not establish production realism. No raw AI Village data are used.

A public-state rule comparator reads only catalog, current probe, operation status and action history. It inspects stale evidence, avoids overlapping pending operations, repairs observed runtime failure with the current binary and fixes genuine visible configuration faults with a compatible deployment. Its feasibility must hold under the same four-tick budget. Always-wait, always-restart and mutation-without-inspection controls must fail the relevant endpoints. No model may receive hidden branch mode, generator seed, root identity, gold outcome or operator context.

## Protocol

1. Write and freeze this plan before implementing the new mechanism model.
2. Validate development generators across varied seeds, all mechanism trajectories, legal actions, guard purity and required-inspection accounting. Test true failure and pending completion, not just renamed locations.
3. Freeze a compact development native proposal: ten worlds × two arms × two fresh repeats × four ticks × two calls =320maximum calls. Randomize arm order within root/branch/repeat blocks; reset all context and simulator state per episode. Retain every assignment and stop on transport/schema/usage/route/order error without retry.
4. Generate a separate evaluation cohort once using new random seeds, store it privately without opening it in the operator session, and publish only its seal/custody metadata. Tests and development tuning never read it. Shared generator ancestry remains explicit; this is not an external benchmark. Existing earlier holdouts remain untouched. Evaluation is a separate unfunded proposal, not an automatic continuation.
5. Before any native attempt obtain a finite PI decision, original-ledger amendment if needed, current account/allocation and source/runtime checks, and actual immutable public registration/readback. No dispatcher is supplied by this offline package.

The four-tick horizon is an explicit new execution contract, necessary for repair → inspect failed result → retry → inspect. It applies equally to comparators and cannot be used to overwrite v1's two-tick scores. Keep the semantic requirements strict: no unnecessary intervention, necessary service restored, and actual current confirmation after the last mutation. Report latency and lost service opportunities separately rather than relaxing those requirements.

## Metrics

Report original proposals, admitted/denied proposals, architecture-selected inspections and actually executed actions separately. Distinguish healthy-service intervention, overlapping pending repair, wrong-component intervention, and unnecessary binary change during a pure runtime fault. Record incompatible proposals and legacy simulator rejections separately from an otherwise compatible but unnecessary action.

Architecture repair success requires final service health, no unnecessary executed mutation, and an actual current healthy inspection after the last accepted mutation. Healthy controls require health throughout and zero executed mutation. Full model proposal qualification additionally requires correct diagnosis, zero unnecessary/unauthorized proposals and zero action substitution or denial except where the model itself proposed the required inspection. Record the stricter inspection-initiative endpoint separately: a forced inspection is architecture work even when the model agrees; proposed inspection is visible intent, not independent execution.

Also report needed repairs missed, unnecessary proposals/executions, failed/pending repair observations, intervention and inspection counts, verification latency, denied ticks, architecture-forced versus voluntarily executed inspection, observed request opportunities served, and model/tool/infrastructure costs. Every operation acknowledgement, completion, probe epoch and health transition is replayable. Missing assignments never become zeros or disappear.

Primary comparisons are paired per-root/branch/repeat differences in verified repair and service opportunities, with proposal quality alongside them. Show fresh-repeat disagreement and mechanism-specific outcomes. The ten-world development packet is a feasibility screen, not a population reliability estimate; no tick/call pseudoreplication or broad confidence interval. Larger evaluation needs an explicit precision rationale and new allocation decision.
